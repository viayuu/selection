Long recovery is run in tmux. The wrapper runs exactly the per-arm `report`
commands recorded in `plan.json`, with empty CUDA visibility and two CPU threads.
It provides no train, TEST, timing, LIB or factory command.
The original frozen reporter and its checkpoint identity checks are reused as-is.

and CPU child logs are hash-bound in `recovery_complete.json`. No automatic retry
occurs after a failed attempt; inspect `attempt.json` and the first fatal log.

Both CPU reports completed successfully at 00:19 on 2026-10-26. The successful
receipt and its exact original generator bytes remain preserved in
`recovery_complete.json` and `report_generator_v1.json`; API additions did not
rerun report rendering or rewrite the successful receipt.

The new helper exposes `analyze`, `wait --publish`, and `publish` through a private
in-memory copy of the unchanged original finisher. Its completion gate accepts
the original failed dispatch plus the independently verified recovery receipt.
`finish_adapter.json` records exact original finisher bytes, the private render
wording replacement, and the exact recovery-only publication additions. No disk
runtime source is patched and no original failure is represented as success.

After complete recovery and successful saved-prediction analysis, the main
finisher may explicitly run
`python -B -m code.V4.r112_postprocess_recovery wait --publish`. The original
global Git publication mutex and single-attempt commit/push policy remain in
force. Recovery itself never calls Git and never publishes partial outputs.

## Readiness Handoff

`readiness.json` records exact per-arm CPU argv, input/source hashes, `verify_argv`
and identical `finish_argv` / `watcher_argv` using only the new helper module.
Consumers must verify `recovery_complete.json` through the verifier,
not infer completion from existence of this directory. CPU recovery does not
grant authorization to launch any GPU process or to stop an existing process.
