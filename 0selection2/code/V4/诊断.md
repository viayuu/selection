我认为有两个结论：

**第一，训练速度快大概率不是数据没跑，而是 R31/R32 的训练循环本来就很轻。**
**第二，R32b 没改善不是因为 attention 不够大，而是因为它现在的“强结构”没有真正打到 R25 的有效机制：support shortlist / solver prior / SBS-safe calibration / top3 排序。**

---

## 1. 先说速度：1 个 epoch 1 分钟多不一定是 bug

从代码看，R32b 每个 step 是“一个 problem 的一个 batch”，不是 18 个 problem 合成一个大 batch。训练循环是：

```python
train_iters = {p: iter(train_loaders[p]) for p in problems}
active = list(problems)
while active:
    random.shuffle(active)
    for problem in list(active):
        batch = next(train_iters[problem])
        ...
        loss.backward()
        optimizer.step()
```

也就是说，假设每个 problem 训练集 10000，`batch_per_problem=384`，那么每个 problem 约 26 个 batch，18 个 problem 约 468 step/epoch。这个数量和你日志里 R31/R32 每个 epoch 几百 step 是对得上的。代码里的 DataLoader 也是按 `batch_per_problem` 分 problem 加载，并且 train 时 `drop_last=True`。

所以如果你的日志里每个 epoch 大约是：

```text
300~500 steps/epoch  # batch 384/512 附近
900+ steps/epoch     # batch 192 附近
```

那速度快是合理的，不是少跑数据。R31 的脚本还默认开了 `--amp --amp-dtype fp16`，batch-per-problem 默认 192，这本身就会很快。

真正要查的是这个：

```python
expected_steps = sum(len(train_loaders[p]) for p in problems)
print("expected_steps_per_epoch", expected_steps)
```

如果实际 `global_step` 每个 epoch 增量等于这个数，就没问题。
如果每个 epoch 只有几十 step，那才是 dataset length / DataLoader 出问题。

---

## 2. R32b 没明显改善的第一大原因：你以为打开的两个关键改动，默认其实没打开

R32b 代码里确实加了：

```python
--top-focused-pair
--topk-ce-weight
```

但默认是：

```python
top_focused_pair = False
topk_ce_weight = 0.0
```

也就是说，如果你的启动命令没有显式加：

```bash
--top-focused-pair
--topk-ce-weight 0.05
```

那么 R32b 的“top-focused pair”和“top-k CE”基本没有进入训练。代码里 `selector_loss` 虽然计算了 `topk_ce`，但只有乘上 `args.topk_ce_weight` 后才进入总 loss；默认这个权重是 0。 

所以 R32b 可能实际上只是：

```text
R32a + support_score_weight=g0 + 多保存几个 checkpoint
```

而不是我之前建议的真正 top3/listwise 修复版。

---

## 3. 第二大原因：R32b 的 top-k CE 形式本身有问题

即使你打开了 `--topk-ce-weight`，现在这个实现也不理想：

```python
for k, weight in enumerate(rank_weights):
    total += weight * F.cross_entropy(logits, rank[:, k])
```

这相当于用同一组 logits 同时做：

```text
第 1 名应该是 label
第 2 名也应该是 label
第 3 名也应该是 label
```

但 softmax CE 是单标签目标。它会让 rank1/rank2/rank3 互相竞争，容易把 top1 margin 拉平，而不是学出正确的 top1/top2/top3 顺序。

更合理的是 Plackett-Luce / sequential CE：

```python
rank = costs.argsort(dim=1)
loss = 0
available = torch.ones_like(logits, dtype=torch.bool)

for k, w in enumerate([1.0, 0.4, 0.2]):
    masked_logits = logits.masked_fill(~available, -1e9)
    target = rank[:, k]
    loss += w * F.cross_entropy(masked_logits, target)
    available.scatter_(1, target[:, None], False)
```

或者直接用 multi-positive BCE：

```text
top1 权重大
top2/top3 权重小
非 top3 负样本
```

现在这个 `ranked_topk_ce_loss` 不应该作为主 top3 修复手段。

---

## 4. 第三大原因：top-focused pair 里的 SBS 是 batch 内 SBS，不是真 SBS

`top_focused_pair_loss` 里有：

```python
sbs = costs.mean(dim=0).argmin()
```

这是**当前 mini-batch 的平均最优 solver**，不是整个 train/val split 的 SBS。

这会导致一个问题：同一个 problem，不同 batch 的“sbs”会变。于是你以为在训练：

```text
best > true SBS
```

实际训练的是：

```text
best > 当前 batch 上碰巧均值最低的 solver
```

这个信号会抖，尤其 CVRP / MVRP 这种 solver 间差距小、batch 内方差大的问题。
如果你打开了 `--top-focused-pair`，这个 loss 可能反而引入噪声。

修法很简单：在 dataset 初始化时预先算好每个 problem 的 train-SBS pool index，然后 batch 里带进去，或者 `selector_loss` 传入全局 `sbs_idx[problem]`。

---

## 5. 第四大原因：R32b 仍然没有复现 R25 的 hard shortlist 机制

历史 R25 的有效点不是“support 分支存在”，而是 support 可以变成 shortlist / mask，把候选集合收窄。旧代码里有 `shortlist_from_support`，会根据 support logits 做 threshold/topk，然后把非 shortlist 的 logits 置为 `-inf`。

但 R32b 里 support 是这样用的：

```python
support_prob = sigmoid(support_logits)
support_max = support_prob.max(dim=1)
support_mean = support_prob.mean(dim=1)
solver_token = solver_token + support_feature_proj(...)
support_score = support_logits[:, 0]  # g0
logits += support_score_weight * support_score
```

也就是说，它没有 hard shortlist；它只是把 support 信息加进 token，再加一点 G0 score。 

这解释了为什么：

```text
top1 还能接近
top3 明显低于 R25
mean cost 也没追上
```

因为 R25 的 top3 高，很可能来自“候选召回/过滤”机制；R32b 现在仍然是全 pool soft ranking，只是多了 support 辅助分数。

---

## 6. 第五大原因：support 特征会把 rank2/rank3 信息污染进 top1 token

R32b 虽然用 `support_score_mode=g0`，但在更新 solver token 时用了：

```python
support_max = support_prob.max(dim=1)
support_mean = support_prob.mean(dim=1)
support_prob.transpose(1, 2)
solver_token = solver_token + support_feature_proj(...)
```

`support_max` 是所有 generator 的 max。可是 rank-partition 下：

```text
G0 学 rank1
G1 学 rank2
G2 学 rank3
G3 学 near-opt / eps
```

所以 `support_max` 会把 rank2/rank3/near-opt 的高分也注入 solver token。最终 utility head 看到的不是纯 top1 信号，而是“这个 solver 是否在 support top candidates 中”。这对 top3 可能有利，但对 top1 排序会变钝。

这和你结果吻合：R32b 的 top1 没明显变好，top3 也没恢复到 R25，因为它既没有 hard shortlist，又把 support 分支软混进 final scorer，形成模糊信号。

---

## 7. 第六大原因：R32 的 KQV attention 其实不是 solver-conditioned instance attention

你现在的核心 attention 是：

```python
query = f(h_cls, cond)
key/value = solver memory
query_logits = query @ solver_key
pre_score = gated sum over query_logits
context = pre_prob @ solver_value
```

也就是说，它是在做：

```text
problem/instance summary -> solver memory attention
```

不是：

```text
每个 solver 分别去看 instance nodes
```

每个 solver 最后拿到的是同一个 `h_cls`、同一个 `cond`、同一个 `context`，再加上自己的 solver memory。

所以它并没有真正做到：

```text
solver A 看 depot/demand/TW 的一套模式
solver B 看另一套模式
```

这点很重要。它看起来是 KQV attention，但表达力未必强过 R25 那套显式 pair feature + problem-solver bias + support shortlist。R32 的 attention 更像是一个高效的 solver-memory mixer，而不是强 solver-conditioned reader。

---

## 8. 结果层面的直接证据：R32b 仍然是 ATSP 强、TSP/CVRP/VRP 不够稳

R32b 相对 R25：

```text
ALL top1: 0.4607 vs 0.4609，基本持平/略低
ALL top2: 0.7898 vs 0.8013，低
ALL top3: 0.9148 vs 0.9337，低很多
mean cost: 11.1845 vs 11.1700，差
```

它最强的还是 ATSP：

```text
ATSP top1: 0.766 vs R25 0.552
```

但被这些问题拖住：

```text
CVRP: 0.379 vs R25 0.466
VRPB: 0.512 vs R25 0.481，top1略好但 mean cost 更差
VRPTW: 0.411 vs R25 0.460
OVRPTW: 0.454 vs R25 0.459
OVRPBTW: 0.495 vs R25 0.523
OVRPLTW: 0.477 vs R25 0.506
```

这说明 R32b 的结构在 ATSP 上很有效，但在 routing coordinate family 上没有继承 R25 的稳定选择策略。

# 我认为真正原因排序

## 最可能的 4 个原因

1. **R32b 的关键新增 loss 可能默认没开**：`top-focused-pair=False`，`topk_ce_weight=0.0`。
2. **如果 top-k CE 开了，当前实现也不对**：同一 logits 同时 CE rank1/rank2/rank3，会冲突。
3. **support 没有 hard shortlist，只是软加分**：没有复现 R25 top3 高的核心机制。
4. **KQV attention 没有让每个 solver 分别读 instance tokens**：只是 instance summary 到 solver memory 的 attention，不是 solver-conditioned instance matching。

速度快这件事，我现在不认为是主要 bug；除非你打印出来发现每个 epoch 的 step 数明显小于 `sum(len(train_loader[p]))`。

# 我建议的 R32c 改法

## 改法 1：把 R25 的 hard shortlist 机制搬回来

不要只做：

```python
logits += 0.1 * support_logits[:, 0]
```

而是评估时加一个版本：

```python
shortlist = union_topk(support_logits, k=2 or 3)
rerank_logits = logits.masked_fill(~shortlist, -inf)
```

先不训练，直接 test/val 试：

```text
final logits
final logits + g0
final logits masked by support union@2
final logits masked by support union@3
pre/gap/utility masked by support union@2/3
```

如果 masked 版本 top3/mean cost 回升，说明 R25 的关键机制就是 shortlist，不是 backbone。

---

## 改法 2：废掉当前 ranked_topk_ce_loss，换成 sequential rank loss

当前这个不要继续用。换成：

```python
def pl_topk_loss(logits, costs, weights=(1.0, 0.4, 0.2)):
    rank = costs.argsort(dim=1)
    available = torch.ones_like(logits, dtype=torch.bool)
    loss = logits.sum() * 0
    denom = 0.0
    for k, w in enumerate(weights):
        if k >= logits.size(1):
            break
        masked = logits.masked_fill(~available, -1e9)
        target = rank[:, k]
        loss = loss + w * F.cross_entropy(masked, target)
        available.scatter_(1, target[:, None], False)
        denom += w
    return loss / denom
```

这才是真的 top1/top2/top3 顺序监督。

---

## 改法 3：top-focused pair 里的 SBS 改成全局 SBS

不要在 batch 内算：

```python
sbs = costs.mean(dim=0).argmin()
```

改成：

```python
sbs_idx = batch["sbs_idx"]  # 每个 problem 固定
```

或者训练时传：

```python
sbs_idx_by_problem[problem]
```

这能减少 loss 噪声。

---

## 改法 4：support 特征拆成 top1 support 和 recall support 两条路

现在 `support_max/mean/all_generators` 混进 solver_token。建议改成：

```text
G0：只服务 final top1
G1/G2/G3：只服务 shortlist/top3，不直接影响 utility head
```

具体：

```python
support_g0_feat = support_logits[:, 0]
support_recall_feat = support_prob[:, 1:].max(dim=1).values

logits += w_g0 * support_g0_feat
# recall_feat 只用于 shortlist mask，不进入 utility token
```

否则 rank2/rank3 头会持续污染 top1 排序。

---

## 改法 5：别指望 R32 单模型替代 R25，先做 R25/R32 family gate

目前实证已经很清楚：

```text
R32 系列：ATSP 强
R25：TSP/CVRP/top3/mean-cost 稳
```

下一步最高 ROI 是：

```text
val 上按 problem/family 选择 R25 或 R32b
```

不要先做复杂 learned gate。先做 rule：

```text
ATSP 用 R32b
TSP/CVRP 大概率用 R25
其余 MVRP 按 val mean cost 或 top1 选择
```

如果这个 hybrid 明显超过两者单独结果，就说明“专家互补”是真方向。

---

## 最后一句判断

R32b 现在不是“模型明明更强但莫名其妙没提升”。更准确地说：

> R32b 的 encoder/attention 更复杂，但它没有继承 R25 最有效的 shortlist / SBS-safe / solver prior 机制；新增的 top-k 训练项默认可能没开，开了也有目标冲突；KQV 结构也不是 solver-conditioned instance attention。因此结果不如 R25 是合理的，不是单纯训练没跑够。

我会先查 `args.json` 和 epoch step 数；如果没问题，下一版优先做 **R25 hard shortlist 复刻 + sequential top-k loss + 全局 SBS top-focused pair**。
