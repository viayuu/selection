我认真想了一下。你的新方案**可行，而且值得做成最高优先级主线**，但我会稍微修正它的实现方式：

> **“problem instance 作为 Q，solver 作为 K/V”这个方向可以成立；但不要只取 attention 后的 pooled vector 再分类。最好的实现是：attention logits 本身就是 solver score，同时保留 solver 轴，再接一个 solver-set Transformer / scoring head。**

原因很简单：如果你做

```text
q = instance embedding
K,V = solver embeddings
context = Attention(q, K, V)
prob = MLP(context)
```

那 `context` 是所有 solver value 的加权平均，一旦平均完，**solver 维度已经被压掉了**。你后面再算 `prob`，其实是在让一个混合向量重新猜 solver，这会损失“每个 solver 为什么匹配这个 instance”的细节。

更合理的是：

```text
score_s = compatibility(q_instance, k_solver_s)
prob_s = masked_softmax(score_s)
context = Σ_s prob_s * v_solver_s    # 这个可以作为辅助，不是主输出
```

也就是说，**attention weight / attention logit 本身就是 selector 的核心输出**。

# 1. 你的思路本质上是什么？

你的新模型可以理解成一个 **Problem-to-Solver Attention Selector**：

```text
给定 routing instance x
→ 用 Transformer 编码成 problem query q(x)
→ 把所有候选 solver 编码成 solver memory {k_s, v_s}
→ 用 q(x) 去检索 / 匹配 solver memory
→ 输出 P(solver | instance)
```

形式上：

```python
Q = W_q h_x                         # (B, R, d)
K = W_k E_solver                    # (B, S, d)
V = W_v E_solver                    # (B, S, d)

attn_logits = Q @ K.transpose(-1, -2) / sqrt(d)   # (B, R, S)
```

如果只有一个 problem query：

```python
score_s = attn_logits[:, 0, s]
prob_s = softmax(masked(score_s))
```

如果有多个 problem query：

```python
score_s = aggregate_r( attn_logits[:, r, s] )
prob_s = softmax(masked(score_s))
```

这个范式非常符合你的任务定义：你不是在生成 route，而是在给定一个 instance 后，从候选 solver 池里检索最匹配的 solver。你的项目本身也是“给定 routing instance，在当前问题可用 solver pool 中选出应该调用的 solver”，并且覆盖 TSP / CVRP / ATSP / 15 个 MVRP 共 18 个 routing problems。

# 2. 我对“problem 作为 Q，solver 作为 K/V”的判断

## 2.1 这个方向是合理的

从任务语义上看，你的直觉是对的：

```text
instance 是当前 query
solver pool 是可检索 memory
selector 要从 memory 里找一个最合适的 solver
```

所以 `problem-as-query, solver-as-key/value` 可以自然地解释为：

```text
这个 instance 正在问：哪个 solver 和我最匹配？
```

这和标准 attention 定义是吻合的。Transformer 里的 attention 本来就是用 query 和一组 key-value pairs 做兼容性匹配，再对 value 加权求和；attention score 可以直接看作 query 对每个 key 的匹配程度。([arXiv][1])

而且 solver 数非常小：

```text
global solver 约 18 个
每个 problem 有效 solver 约 3–10 个
```

所以对 solver set 做 full attention 几乎没有计算压力。相比 node-level attention，solver-level attention 是便宜的。

---

## 2.2 但我要强调：Q/K/V 的“语义直觉”不能压过“输出形状”

attention 里谁做 Q，最重要的不是“谁主动找谁”，而是：

> **Q 的长度决定输出 token 的长度。**

如果你设：

```text
Q = problem token，长度 1
K/V = solver tokens，长度 S
```

那么输出是：

```text
一个 problem-conditioned context vector
```

而不是：

```text
S 个 solver-conditioned utility vectors
```

所以这条路最适合做：

```text
直接用 attention logits 产生 P(solver | instance)
```

而不是：

```text
attention 后得到一个 context，再从 context 分类
```

如果你想让每个 solver 都有自己的 refined representation，那么更自然的是：

```text
Q = solver tokens
K/V = instance tokens
```

这其实你之前的代码里已经做过类似版本：`ArmAttentionHead` 里是“每个 solver embedding 作为 query，node tokens 作为 keys/values”，目的是让每个 arm 自己 attend instance token，打破单个 pooled embedding 和 solver embedding 做点积的瓶颈。

所以我的建议不是二选一，而是：

> **第一层用 problem-as-query 去 solver memory，得到 solver-level compatibility；第二层保留 solver tokens，做 solver-set refinement。**

这样既尊重你的直觉，又不丢 solver 轴。

# 3. 单 query 版本的表达能力：它其实等价于“attention 化的分类器”

先看最小版本：

```python
q = f_instance(x)        # (B, d)
k_s = f_solver(s)        # (S, d)
score_s = q @ k_s / sqrt(d)
prob_s = softmax(score_s)
```

这本质上是一个 **bilinear / metric-learning classifier**。

它的优点：

```text
1. 非常干净
2. 很容易训练
3. 直接得到 solver probability
4. 天然支持 mask
5. 可以把 solver 当成 memory item，而不是普通 class id
```

但它也有明显限制：

```text
score_s = q^T k_s
```

如果只有一个 q，它对所有 solver 的评分都是在同一个 embedding 空间里做线性匹配。这个能力可能不够表达：

```text
某些 solver 关心 instance 的局部聚类结构
某些 solver 关心 time window tightness
某些 solver 关心 backhaul / negative demand
某些 solver 关心 asymmetric matrix pattern
某些 solver 只在特定 problem + size + distribution 下好
```

所以我不建议最终停在 single-query dot-product。它可以做 R31a sanity，但不是最终版。

---

# 4. 我建议的最终结构：Multi-Query Problem-to-Solver Attention + Solver-Set Transformer

我会把你的方案设计成三段。

---

## 4.1 Instance Transformer Encoder

输入 instance tokens。

对坐标类问题：

```text
node_i = [
  x_i, y_i,
  demand_i,
  demand_sign / backhaul flag,
  is_depot,
  tw_start,
  tw_end,
  route_limit feature,
  service_time,
  valid_field_mask
]
```

再加几个 global tokens：

```text
[CLS]
[PROBLEM]
[CONSTRAINT]
[STATS]
```

其中 `[PROBLEM] / [CONSTRAINT]` 要显式吃：

```text
problem_id
problem_family
constraint bits: C/O/B/L/TW
coord_dist / size_bin
manual/global stats
```

然后：

```python
H = InstanceTransformer(tokens, attention_bias)
h_cls = H[:, cls_index]
```

这里的 instance transformer 可以先不用太复杂。第一版建议：

```text
d_model = 128
layers = 4
heads = 4
dropout = 0.1
norm_first = True
```

你也可以逐步加 URS-style relation bias，但这个不是第一天必须做的。

---

## 4.2 Solver Memory Encoder

不要让 solver 只是一个 learned ID。每个 solver token 应该是：

```text
solver_token_{p,s} = [
  solver_id_embedding,
  solver_family_embedding,
  problem_id_embedding,
  problem_solver_arm_embedding,
  availability_embedding,
  optional empirical stats,
  constraint-conditioned adapter
]
```

具体：

```python
e_s = solver_id_emb[s]
e_p = problem_emb[p]
e_arm = arm_emb[p, s]             # 很重要
e_family = solver_family_emb[fam_s]
z_s = concat(e_s, e_p, e_arm, e_family, solver_meta)
m_s = SolverFFN(z_s)
```

然后：

```python
K_s = W_k m_s
V_s = W_v m_s
```

这里我强烈建议加入 `problem_solver_arm_embedding[p, s]`。因为同一个 solver 名字在不同 problem 下不一定表示同一种行为。例如 LEHD 在 TSP 和 CVRP 下的角色不同，MVMOE 在不同 MVRP 变体下的表现也不同。如果只有 global solver embedding，模型会被迫学一个过度平均的 solver 表征。

---

## 4.3 Multi-Query Problem-to-Solver Attention

不要只用一个 query。建议从 instance 表征里生成多个 problem query：

```python
Q = QueryGenerator(h_cls, H, condition)   # (B, R, d)
```

其中：

```text
R = 4 或 8
```

每个 query 可以代表一种“选择视角”：

```text
q0: global best-solver tendency
q1: geometry / local structure
q2: constraint-specific preference
q3: size / distribution / difficulty
q4: rare / niche solver trigger
...
```

实现上不需要显式命名，只要学习即可：

```python
q_base = self.query_seed[None, :, :]          # (1, R, d)
q_cond = self.query_gen(condition).view(B,R,d)
Q = q_base + q_cond + self.cls_to_q(h_cls).view(B,R,d)
```

然后 cross attention：

```python
raw = torch.einsum("brd,bsd->brs", Q, K) / sqrt(d)
raw = raw.masked_fill(~solver_mask[:, None, :], -1e9)
```

接下来不要简单平均 query。建议用 instance-conditioned gate 聚合：

```python
gate = softmax(MLP(h_cls), dim=-1)      # (B, R)
score_s = Σ_r gate_r * raw_{r,s}
```

也可以用 head/query 的 logsumexp 聚合：

```python
score_s = logsumexp_r(raw_{r,s} + gate_logit_r)
```

这个比单 query 强很多，因为它允许同一个 instance 用多个角度去匹配 solver。

---

# 5. 关键点：attention 后不要丢 solver 轴

你的原始描述是：

```text
problem embedding as q
solver embedding as kv
attention
then prob
```

我建议具体改成：

```text
problem embedding as q
solver embedding as k/v
attention logits = preliminary solver scores
attention values/context = auxiliary representation
solver tokens + preliminary scores → set transformer → final scores
```

也就是：

```python
attn_logits = Q @ K.T / sqrt(d)       # (B, R, S)
pre_score = aggregate(attn_logits)    # (B, S)

attn_prob = softmax(pre_score + mask) # (B, S)
context = attn_prob @ V               # (B, d)

solver_features = [
  solver_memory,
  pre_score,
  pre_prob,
  context broadcast,
  condition broadcast
]

refined_solver_tokens = SolverSetTransformer(solver_features)
final_score_s = score_head(refined_solver_tokens_s)
prob_s = masked_softmax(final_score_s)
```

为什么要加 `SolverSetTransformer`？

因为 solver selection 不是独立打分，而是候选集合内的相对选择。Set Transformer 的思路正适合这种“输入是一组无序候选元素，需要建模集合内交互”的场景；它用 attention 建模 set elements 之间的关系，并保持 permutation-invariant / equivariant 的结构。([arXiv][2])

在你的任务里，solver pool 是一个小集合：

```text
TSP: 10
CVRP: 9
ATSP: 3
MVRP: 4
```

所以 solver-set self-attention 非常便宜。你完全可以加 1–2 层：

```python
nn.TransformerEncoderLayer(
    d_model=d_solver_token,
    nhead=4,
    dim_feedforward=4*d_solver_token,
    batch_first=True,
    norm_first=True,
)
```

# 6. 我推荐的完整模型命名：P2S-Transformer

可以叫：

```text
P2S-Transformer = Problem-to-Solver Transformer Selector
```

完整 forward：

```python
def forward(batch):
    # 1. encode instance
    H, h_cls, condition = instance_encoder(batch)

    # 2. build problem queries
    Q = problem_query_generator(h_cls, condition)      # (B, R, d)

    # 3. build solver memory
    solver_ids = all_global_solvers or pool_solvers
    M = solver_encoder(solver_ids, batch.problem_id, condition)  # (B, S, d)

    K = Wk(M)
    V = Wv(M)

    # 4. problem-to-solver attention
    logits_r = einsum(Q, K) / sqrt(d)                  # (B, R, S)
    logits_r = mask_invalid(logits_r, solver_mask)

    gate_r = softmax(query_gate(h_cls), dim=-1)        # (B, R)
    pre_score = (gate_r[:, :, None] * logits_r).sum(1) # (B, S)

    pre_prob = masked_softmax(pre_score, solver_mask)

    # 5. optional context
    context = pre_prob @ V                             # (B, d)
    context_broadcast = context[:, None, :].expand(-1, S, -1)

    # 6. solver set refinement
    Z = concat([
        M,
        pre_score[..., None],
        pre_prob[..., None],
        context_broadcast,
        condition[:, None, :].expand(-1, S, -1),
    ], dim=-1)

    Z = solver_set_transformer(Z, src_key_padding_mask=~solver_mask)

    # 7. final heads
    final_score = utility_head(Z).squeeze(-1)
    pred_gap = gap_head(Z).squeeze(-1)

    final_score = final_score - lambda_gap * pred_gap
    final_score = mask_invalid(final_score, solver_mask)

    return final_score, pred_gap, pre_score, pre_prob
```

# 7. 训练目标怎么配？

我建议不要只用 CE。这个结构很适合多目标训练：

```text
L =
  0.35 * winner_CE(final_score)
+ 0.30 * pairwise_rank_loss(final_score, true_cost)
+ 0.20 * cost_gap_regression(pred_gap, true_gap)
+ 0.10 * pre_attention_CE(pre_score)
+ 0.05 * query_diversity_regularization
```

解释一下。

## 7.1 Winner CE

```python
L_ce = CE(masked_logits, oracle_winner)
```

这是最直接的 top1 监督。

## 7.2 Pairwise rank loss

对同一个 instance 的 solver pool 内任意两个 solver：

```python
if cost_i < cost_j:
    score_i should > score_j
```

loss：

```python
L_pair = softplus(-(score_i - score_j)) * margin_weight
```

其中：

```python
margin_weight = clip(abs(cost_i - cost_j) / tau, 0.2, 5.0)
```

这比 CE 更充分，因为 CE 只告诉你 winner 是谁，pairwise loss 告诉你整个 solver pool 的相对顺序。

## 7.3 Cost-gap regression

预测：

```python
target_gap_s = (cost_s - cost_sbs) / abs(cost_sbs)
```

loss：

```python
L_gap = Huber(pred_gap_s, target_gap_s)
```

这能让模型不要只学“分类标签”，而是学 solver 的真实效果差异。

## 7.4 Pre-attention CE

让 `problem-to-solver attention` 本身也能选 solver：

```python
L_pre = CE(pre_score, oracle_winner)
```

否则模型可能把前面的 attention 当成无意义中间层，所有选择能力都压到最后 MLP。

## 7.5 Query diversity

如果你用 `R=4/8` 个 problem queries，要防止所有 query 学成一样。可以加：

```python
A = softmax(logits_r, dim=-1)    # (B, R, S)
div_loss = mean cosine_similarity(A_r, A_t), r != t
```

或者让不同 query 的 solver distribution 不要完全重合：

```python
L_div = mean_{r<t} dot(A_r, A_t)
```

权重小一点：

```text
0.01 ~ 0.05
```

不要太大，否则会为了多样性乱选。

# 8. 为什么这个新方案比“普通 masked softmax 分类器”更有意义？

如果只是：

```python
h = instance_encoder(x)
logits = Linear(h)
```

那么 solver 只是 class index。

你的新方案变成：

```python
solver 是 memory item
instance 是 query
score = compatibility(instance, solver)
```

这有几个优点。

第一，它把 solver 从“类别编号”变成“可比较对象”。这更接近推荐系统里的 item retrieval：用户/query 和 item/solver 在同一个匹配空间里做检索。

第二，它天然支持不同 problem 的 solver pool mask。你只需要：

```python
score_s = -inf if solver not available
```

第三，它更容易扩展 solver features。比如你以后给 solver token 加：

```text
solver family
training-time performance profile
problem-specific arm embedding
mean rank prior
cost-gap prototype
```

模型可以自然通过 K/V 使用这些信息，而不是把所有东西塞进最后一个分类头。

第四，它可以解释 attention 权重。至少可以看：

```text
which query attends to which solver
which solver key matched current instance
```

虽然这不是严格解释性，但比普通 MLP head 更容易诊断。

# 9. 这个方案的主要风险

## 风险 1：single-query 退化成低秩分类器

如果只有一个 query：

```python
score_s = q^T k_s
```

这就是低秩 factorized classifier。它可能比当前 head 更干净，但不一定更强。

解决：

```text
1. 用 multi-query
2. 加 pairwise / listwise loss
3. 加 solver-set transformer
4. score head 不只用 q^T k_s，也用 [q, k_s, q*k_s, |q-k_s|]
```

推荐 scoring：

```python
pair_feat_s = concat([
    q_global,
    k_s,
    q_global * k_s,
    abs(q_global - k_s),
    pre_score_s,
    solver_meta_s,
    condition,
])
score_s = MLP(pair_feat_s)
```

这样 attention logit 是一个重要特征，但不是唯一特征。

---

## 风险 2：solver V 被平均后丢失选择信息

如果你最后只用：

```python
context = Σ p_s v_s
prob = MLP(context)
```

那很危险。因为 `context` 已经混合了 solver 信息，尤其当 top2/top3 solver 很接近时，这个混合向量会变得模糊。

解决：

```text
final probability 直接来自 per-solver score
context 只作为辅助 feature
```

---

## 风险 3：solver embedding 过弱，变成 fancy class embedding

如果 solver encoder 只输入：

```python
solver_id
```

那它和普通分类头区别不大。

解决：

```text
solver token = solver id + problem id + problem-solver arm id + solver family + empirical performance profile
```

尤其是：

```python
arm_emb[p, s]
```

这个非常重要。

---

## 风险 4：problem query 不知道当前 problem semantics

你的任务里有一个特殊难点：某些问题输入格式可能很像，但实际 problem semantics 不同。项目文档里也提到，不同问题支持 solver 数量不同、部分 solver 交叉，且 OVRP 等问题可能和 CVRP 输入格式相似，模型必须知道当前实例到底属于什么 problem。

所以 `q_instance` 不能只来自 node transformer。它必须融合：

```text
problem_id
constraint bits
problem family
coord_dist / size_bin
manual/global stats
```

否则 attention query 会把“输入长得像”的问题混起来。

# 10. 我建议的三个版本

## Version A：最小可行版

目的：验证你的核心想法。

```text
Instance Transformer → h_cls
Solver FFN → K,V
single/multi query attention → score_s
masked softmax → CE + pairwise loss
```

结构：

```python
score_s = q @ k_s / sqrt(d) + problem_solver_bias[p,s]
```

训练：

```text
CE + pairwise rank
```

优点：

```text
简单，容易 debug
```

缺点：

```text
可能表达力不够
```

这版可以叫：

```text
R31a_p2s_attention_minimal
```

---

## Version B：推荐主版本

目的：真正替代当前 selector。

```text
Instance Transformer
+ Multi-query problem-to-solver attention
+ Solver-set Transformer
+ utility head + gap head
```

结构：

```python
pre_score = P2SAttention(Q_problem, K_solver)
Z_solver = SolverSetTransformer([solver_token, pre_score, pre_prob, condition])
final_score = utility_head(Z_solver) - λ * gap_head(Z_solver)
```

训练：

```text
winner CE
+ pairwise rank
+ cost gap regression
+ pre-attention CE
+ query diversity
```

这版可以叫：

```text
R31b_p2s_set_transformer
```

---

## Version C：双向 cross-attention 完整版

目的：最大化表达能力。

```text
1. problem queries attend solver memory
2. solver tokens attend instance node tokens
3. solver tokens self-attend within candidate pool
4. final score
```

也就是：

```python
Q_problem -> K/V_solver       # instance asks: which solver?
Q_solver  -> K/V_instance     # each solver asks: what instance evidence do I need?
solver self-attention         # solvers compare each other
```

这版结合了你的新想法和之前 solver-query 的优点。Perceiver IO 这类架构也说明，cross-attention 可以很自然地在不同结构的输入/输出之间建立映射，不必拘泥于单一 self-attention 形式。([arXiv][3])

这版可以叫：

```text
R31c_bipartite_p2s_s2p_transformer
```

我建议先跑 A，再跑 B。C 等 B 有明显信号再做。

# 11. 具体 PyTorch 模块草图

下面是一个比较接近可实现的版本。

```python
class ProblemToSolverAttention(nn.Module):
    def __init__(
        self,
        d_model: int = 128,
        n_solver: int = 18,
        n_problem: int = 18,
        n_queries: int = 4,
        n_heads: int = 4,
        dropout: float = 0.1,
        cond_dim: int = 64,
    ):
        super().__init__()
        self.d_model = d_model
        self.n_queries = n_queries

        self.solver_id_emb = nn.Embedding(n_solver, d_model)
        self.problem_emb = nn.Embedding(n_problem, d_model)
        self.arm_emb = nn.Embedding(n_problem * n_solver, d_model)
        self.solver_family_emb = nn.Embedding(8, d_model)

        self.solver_ffn = nn.Sequential(
            nn.Linear(4 * d_model, 2 * d_model),
            nn.GELU(),
            nn.Dropout(dropout),
            nn.Linear(2 * d_model, d_model),
        )

        self.query_seed = nn.Parameter(torch.randn(n_queries, d_model) * 0.02)
        self.cls_to_queries = nn.Linear(d_model, n_queries * d_model)
        self.cond_to_queries = nn.Linear(cond_dim, n_queries * d_model)

        self.q_proj = nn.Linear(d_model, d_model)
        self.k_proj = nn.Linear(d_model, d_model)
        self.v_proj = nn.Linear(d_model, d_model)

        self.query_gate = nn.Sequential(
            nn.Linear(d_model + cond_dim, d_model),
            nn.GELU(),
            nn.Linear(d_model, n_queries),
        )

        solver_feat_dim = d_model + 2 + d_model + cond_dim
        self.solver_token_proj = nn.Linear(solver_feat_dim, d_model)

        enc_layer = nn.TransformerEncoderLayer(
            d_model=d_model,
            nhead=n_heads,
            dim_feedforward=4 * d_model,
            dropout=dropout,
            activation="gelu",
            batch_first=True,
            norm_first=True,
        )
        self.solver_set_encoder = nn.TransformerEncoder(enc_layer, num_layers=2)

        self.utility_head = nn.Sequential(
            nn.LayerNorm(d_model),
            nn.Linear(d_model, d_model),
            nn.GELU(),
            nn.Linear(d_model, 1),
        )

        self.gap_head = nn.Sequential(
            nn.LayerNorm(d_model),
            nn.Linear(d_model, d_model),
            nn.GELU(),
            nn.Linear(d_model, 1),
        )

    def build_solver_memory(self, problem_id, solver_ids, solver_family_ids):
        """
        problem_id: (B,)
        solver_ids: (S,)
        solver_family_ids: (S,)
        returns: (B, S, d)
        """
        B = problem_id.shape[0]
        S = solver_ids.shape[0]

        e_solver = self.solver_id_emb(solver_ids)[None].expand(B, S, -1)
        e_problem = self.problem_emb(problem_id)[:, None, :].expand(B, S, -1)

        arm_index = problem_id[:, None] * self.solver_id_emb.num_embeddings + solver_ids[None, :]
        e_arm = self.arm_emb(arm_index)

        e_family = self.solver_family_emb(solver_family_ids)[None].expand(B, S, -1)

        z = torch.cat([e_solver, e_problem, e_arm, e_family], dim=-1)
        return self.solver_ffn(z)

    def forward(self, h_cls, cond, problem_id, solver_ids, solver_family_ids, solver_mask):
        """
        h_cls: (B, d)
        cond: (B, cond_dim)
        solver_mask: (B, S), True if valid
        """
        B = h_cls.shape[0]
        S = solver_ids.shape[0]

        # solver memory
        M = self.build_solver_memory(problem_id, solver_ids, solver_family_ids)  # (B,S,d)
        K = self.k_proj(M)
        V = self.v_proj(M)

        # problem queries
        Q = self.query_seed[None].expand(B, -1, -1)
        Q = Q + self.cls_to_queries(h_cls).view(B, self.n_queries, self.d_model)
        Q = Q + self.cond_to_queries(cond).view(B, self.n_queries, self.d_model)
        Q = self.q_proj(Q)

        # problem-to-solver compatibility
        logits_r = torch.einsum("brd,bsd->brs", Q, K) / math.sqrt(self.d_model)
        logits_r = logits_r.masked_fill(~solver_mask[:, None, :], -1e9)

        # aggregate queries
        gate = self.query_gate(torch.cat([h_cls, cond], dim=-1))
        gate = torch.softmax(gate, dim=-1)  # (B,R)

        pre_score = (gate[:, :, None] * logits_r).sum(dim=1)  # (B,S)
        pre_score = pre_score.masked_fill(~solver_mask, -1e9)
        pre_prob = torch.softmax(pre_score, dim=-1)

        # context is auxiliary, not final output
        context = torch.einsum("bs,bsd->bd", pre_prob, V)
        context_b = context[:, None, :].expand(B, S, -1)

        solver_features = torch.cat([
            M,
            pre_score.unsqueeze(-1),
            pre_prob.unsqueeze(-1),
            context_b,
            cond[:, None, :].expand(B, S, -1),
        ], dim=-1)

        Z = self.solver_token_proj(solver_features)
        Z = self.solver_set_encoder(Z, src_key_padding_mask=~solver_mask)

        utility = self.utility_head(Z).squeeze(-1)
        pred_gap = self.gap_head(Z).squeeze(-1)

        final_score = utility - 0.5 * pred_gap
        final_score = final_score.masked_fill(~solver_mask, -1e9)

        return {
            "logits": final_score,
            "pre_score": pre_score,
            "pre_prob": pre_prob,
            "pred_gap": pred_gap,
            "query_logits": logits_r,
        }
```

# 12. Instance Transformer 怎么写？

第一版不要写太花。坐标问题：

```python
class InstanceTransformer(nn.Module):
    def __init__(self, d_in, d_model=128, n_layers=4, n_heads=4):
        super().__init__()
        self.node_proj = nn.Linear(d_in, d_model)
        self.cls = nn.Parameter(torch.randn(1, 1, d_model) * 0.02)
        self.problem_proj = nn.Linear(problem_cond_dim, d_model)
        self.stats_proj = nn.Linear(stats_dim, d_model)

        layer = nn.TransformerEncoderLayer(
            d_model=d_model,
            nhead=n_heads,
            dim_feedforward=4*d_model,
            batch_first=True,
            norm_first=True,
            activation="gelu",
        )
        self.encoder = nn.TransformerEncoder(layer, num_layers=n_layers)

    def forward(self, node_feat, node_mask, condition, stats):
        B = node_feat.shape[0]
        node_tok = self.node_proj(node_feat)

        cls = self.cls.expand(B, 1, -1)
        problem_tok = self.problem_proj(condition).unsqueeze(1)
        stats_tok = self.stats_proj(stats).unsqueeze(1)

        tokens = torch.cat([cls, problem_tok, stats_tok, node_tok], dim=1)

        special_mask = torch.ones(B, 3, dtype=torch.bool, device=node_mask.device)
        mask = torch.cat([special_mask, node_mask], dim=1)

        H = self.encoder(tokens, src_key_padding_mask=~mask)
        h_cls = H[:, 0]
        return H, h_cls
```

ATSP 可以先单独走 matrix encoder，然后也输出：

```text
H_matrix_tokens
h_cls
condition
```

不要强行第一版就统一所有 token schema，否则工程量会爆炸。

# 13. 和你之前做过的 solver-query attention 有什么不同？

之前的方向更像：

```text
每个 solver 问 instance：
我应该关注哪些 node？
```

也就是：

```text
Q = solver
K/V = instance tokens
```

你现在的新方向是：

```text
instance 问 solver pool：
哪个 solver 最适合我？
```

也就是：

```text
Q = problem
K/V = solver
```

这两个其实不是冲突，而是互补。

我的判断：

```text
problem→solver attention:
  更适合产生全局选择分布，稳定、直接、像 retrieval

solver→problem attention:
  更适合产生每个 solver 的局部 evidence，表达力强

solver-set self-attention:
  更适合在候选 solver 之间做相对比较
```

所以最终最强结构大概率是：

```text
problem→solver attention 先给粗匹配分
solver→problem attention 给每个 solver 抽取 instance evidence
solver-set transformer 做候选间比较
final score 输出
```

但第一版不要全上。先验证 `problem→solver` 能不能单独成为一个更强 selector。

这个版本最符合你的新思路，同时避免“attention pooled vector 丢 solver 轴”的最大风险。

# 16. 一句话判断

你的新想法是可行的，而且比继续在旧模型后面接 reranker/gate 更值得投入。

但我会把它从：

```text
problem q attends solver kv → 得到一个 context → 再分类
```

改成：

```text
problem q attends solver kv → attention logits 直接是 solver preliminary score
→ 保留 solver 轴 → solver-set transformer refinement
→ final probability
```

这样它才真正成为一个 **attention-based solver selector**，而不是一个“用 attention 做了一次池化的普通分类器”。
