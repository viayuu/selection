# My（Two-Gate RL）项目不足与改进计划（深度审视版）

> 范围声明：本文主要针对 `1two_gate/` 目录（两层 gate + 强化学习的 solver/pipeline 选择原型）做“不足/风险/不合理处”的系统性盘点，并给出一个可执行的改进路线图。  
> 约束假设：尽量只改 `1two_gate/`（通过 `1two_gate/easynco_bootstrap.py` 复用 `EasyNCO/` 的 EasyNCO 组件），不要求改动 `EasyNCO/` 或其它作者代码。

## 本计划基于你的最新三点设定（作为硬约束）

1) **对比口径**：只看 `length`（不考虑 time / gap / wall-clock / 额外开销）  
2) **学习目标**：面对**不同数据分布**，gate 能学会选择不同的初始化器与迭代器（distribution-specific specialization）  
3) **评估开销**：不需要考虑（eval 可以做全量、做 exhaustive、做多 seed 重复）

## 0. 你现在的实现（快速回忆）

### 0.1 核心目标（研究问题）
- 把“选择对象”从 **完整 solver** 拆成两阶段 pipeline：
  - Gate1：选 **初始化器** → 产生 `sol0`
  - Gate2：在 `data + sol0` 条件下选 **迭代器**（固定步数）→ 产生 `sol1`
- 强化学习训练：最终 reward 统一归因到两次决策（两层 gate）。
- 在你最新设定下：**唯一优化目标是最小化 `length(sol1)`**，并希望 gate 在不同分布上产生不同选择（体现偏好性/专长）。

### 0.2 代码主干（数据流）
- 训练入口：`1two_gate/train_two_gate_tsp.py`
  1) 合成 TSP 坐标（`1two_gate/tsp_data.py`）  
  2) 特征提取（默认论文同款 encoder）：`1two_gate/features.py` + `1two_gate/paper_encoder.py`  
  3) Gate1 采样 action → 执行初始化器（`1two_gate/solver_zoo.py`）得到 `sol0`  
  4) Gate2 采样 action → 执行迭代器（`1two_gate/solver_zoo.py`）得到 `sol1`  
  5) `reward=-len(sol1)` 做 REINFORCE/AC（支持 batch mean / critic / 混合）
- 推理入口：`1two_gate/solve_dataset_tsp.py`（加载 gate ckpt，在数据集上执行同样数据流）
- 平台复用：`1two_gate/easynco_bootstrap.py` 在运行时统一处理本地 `EasyNCO/` 的导入与兼容层，避免改平台代码。

## 1. 当前项目的“主要不足”总览（按优先级）

我把不足分成三档：
- **P0（阻断/会导致结论不可信）**：会明显影响正确性、公平性或可复现性
- **P1（重要/会显著影响实验质量）**：能跑但会明显影响稳定性、效率、对比价值
- **P2（提升项/研究扩展）**：更偏研究完整性与论文价值

下面每条都包含：现象 → 为什么是问题 → 建议改法（尽量落在 `1two_gate/`）。

## 2. P0：会直接影响正确性/公平性/可复现性的点

### P0.1 Gate2 特征会 **重复跑一遍 encoder**（隐藏的性能/一致性问题）
- 现象：
  - `tsp_gate2_features()` 内部调用 `tsp_instance_features()` 作为 base（`1two_gate/features.py`）。
  - 训练时 `1two_gate/train_two_gate_tsp.py` 先算了 `feat1=tsp_instance_features(...)` 给 Gate1，再算 `feat2=tsp_gate2_features(...)` 给 Gate2 → **同一个 batch 的 encoder forward 被重复计算**。
- 为什么这是问题：
  1) **训练/推理成本翻倍**：encoder 通常是最重的部分，重复 forward 会直接拖慢实验迭代。
  2) **潜在的不一致**：如果未来把 paper encoder 的 norm 改成 BatchNorm（或引入 dropout），同一个 batch 两次 forward 可能导致统计量/随机性变化，使 Gate2 的 base 特征与 Gate1 不一致（可解释性变差）。
  3) **可扩展性受限**：你后续一旦加入更重的 encoder（如层次 pooling、更多层），重复 forward 会非常痛。
- 建议（最小改动路线）：
  - 把 Gate2 的特征函数拆成两段：
    - `base_feat = tsp_instance_features(...)`（只跑一次）
    - `feat2 = concat(base_feat, length0, tour_stats, ...)`
  - 或者让 `tsp_gate2_features(..., base_feat=...)` 支持传入复用的 base。

### P0.2 评估缺少“Oracle/Regret（含按分布拆解）”基线，导致很难判断 gate 是否真的学到“分布→策略”
- 现象：
  - 当前评估输出主要是 `mean_len` + gate 分布（`1two_gate/train_two_gate_tsp.py:evaluate()`）。
  - 没有**按“分布”维度**拆解：你无法证明“不同分布选择不同 pipeline”。
  - 没有**exhaustive** 评估：你无法知道 zoo 内每个初始化器/迭代器（以及组合）的真实专长版图。
- 为什么这是问题：
  - 你的研究问题是“**分布条件下的 pipeline 选择**”。如果不做 oracle/regret（并按分布拆解），你无法回答三个关键问题：
    1) zoo 里是否真的存在“分布专长”（specialist）？还是某个 solver 全局 dominate？  
    2) gate 选择是否接近“分布内 oracle”（即在该分布下能挑到最优/次优 pipeline）？  
    3) 如果 gate 没学到，瓶颈到底在“识别分布特征”还是“组合信用分配（Gate1 vs Gate2）”？
- 建议：
  - 既然你明确“eval 开销不用考虑”，建议直接把评估做到“学术上很难被质疑”的程度（exhaustive + per-distribution）：
    - **(A) 初始化器单测（len0）**：对每个分布 D，计算每个 initializer `i` 的 `len0(i|D)` 分布与均值、win-rate  
    - **(B) 组合单测（len1）**：对每个分布 D，计算所有 `(init=i, iter=j)` 的 `len1(i,j|D)`（全矩阵）  
    - **(C) Oracle（实例级）**：
      - `oracle_len(inst) = min_{i,j} len1(i,j|inst)`  
      - `gate_regret(inst) = len1(gate(inst)) - oracle_len(inst)`  
      - 并对每个分布汇总 `E[regret|D]`、分位数、tail（例如 top-5% regret）  
    - **(D) 分解 Gate1/Gate2 的责任（credit assignment 诊断）**：  
      - `oracle_init(inst) = argmin_i min_j len1(i,j|inst)`（最优 initializer）  
      - `oracle_iter_given_init(inst, i) = argmin_j len1(i,j|inst)`（给定 initializer 的最优 iterator）  
      - 统计 gate1 选错 vs gate2 选错导致的 regret 占比（你会非常快定位瓶颈）
    - **(E) “是否学到分布选择”的量化指标**：  
      - 计算 `I( D ; a1 )`、`I( D ; a2 )`（互信息/归一化互信息），以及按 D 的 action 分布差异（JS divergence）

### P0.3 如果 zoo 里存在 “全局 dominate” solver，你的研究会退化成“永远选它”（无法证明分布专长）
- 现象：
  - 你希望“不同分布选择不同初始化/迭代”。但如果某个 pipeline 在所有分布上都最好（或几乎最好），那么：
    - gate 的最优策略就是恒等映射（总是选同一个），**研究信号会被冲掉**；
    - 你很难证明“双 gate 的必要性”，因为“选择”本身不再是问题。
- 为什么这是问题：
  - 这不是实现 bug，而是“实验设计风险”：**solver zoo 的构造**决定了你的论文是否有意义。
- 建议（在你只看 length 的设定下，这一点尤其重要）：
  1) **先用 exhaustive eval 画出“专长地图”**（见 P0.2 的全矩阵评估）：确认每个分布上至少存在 2–3 个 pipeline 有互有胜负的区域  
  2) 如果确实有 dominate solver：  
     - 要么把它从 zoo 中移出（让问题重新有意义）  
     - 要么扩大分布跨度/改变 budget/加入更有互补性的 solver，使得不同分布上最优者不同  
  3) 你也可以把目标改成“Top-k selection”（例如给 gate 输出一个候选集合再取 best），但这属于研究方向变更（不建议在原型早期就改）

### P0.4 全局 `torch.set_default_tensor_type` 带来跨组件 device 混用风险
- 现象：
  - `1two_gate/train_two_gate_tsp.py:_configure_torch_defaults()` 会在 CUDA 模式下全局设置默认 tensor type 为 `torch.cuda.FloatTensor`。
- 为什么这是问题：
  - EasyNCO/你自己包装的某些 solver 代码会创建不带 `device=` 的 tensor；当你希望它在 CPU 上跑（或某段逻辑在 CPU 上）时，会发生隐性 device 错配。
  - 这类 bug 特征：**不稳定、难复现、只在某些路径触发**，会极大拖慢研究迭代。
- 建议：
  - 把“切 default tensor type”变成局部 context manager（只包住确实需要的 `EasyNCO/` 调用段），并尽量避免在整个训练进程范围内生效。
  - 对“强制 CPU 跑”的 iterator/initializer wrapper（例如 DACT）统一加保护（你已经对 DACT 做过一次修补，但整个项目仍然存在系统性风险）。

## 3. P1：会显著影响训练稳定性/效率/实验价值的点

### P1.1 Gate 很容易塌缩到单一 solver（缺少显式探索机制）
- 现象：
  - 你记录了 entropy，但没有把 entropy bonus 写入 loss。
- 为什么这是问题：
  - 两层 gate 的探索空间更大；在早期随机波动下，很容易某个 solver 偶然领先 → gate 迅速变成 one-hot → 之后几乎不再探索其它 solver，导致：
    - 你观察到的“偏好性”可能是训练早期随机因素，而非真实实例结构偏好
    - 训练可复现性差（seed 改一下就选不同 solver）
- 建议：
  - 加 `entropy_coef`（可设为 0 默认不影响）：
    - `loss += -entropy_coef * (H(dist1)+H(dist2))`
  - 或引入 epsilon-greedy/temperature schedule。

### P1.2 batch_mean baseline 是“近似无偏”，严格来说会引入 bias（研究写作风险）
- 现象：
  - baseline 用 `mean(length)` 会包含样本自身（与其 action 不完全独立）。
- 风险：
  - 工程上常用，但如果你后面要严谨推导/写论文，可能会被 reviewer 抓住（尤其你强调“严格按 batch mean baseline”时）。
- 建议：
  - 新增一个选项 `loo_batch_mean`（leave-one-out），保持你原本 batch_mean 不动，但提供“严谨版”。

### P1.3 Gate2 条件信息偏弱，可能学不到“初始化×迭代的组合偏好”
- 现象：
  - Gate2 目前使用：`base(data embedding) + length0 + (tour segment mean/std/min/max)`。
- 为什么不够：
  - 很多迭代器的有效性取决于 `sol0` 的结构（交叉数、局部团簇、边分布、候选边质量等），这些统计无法刻画。
- 建议（分层增强）：
  1) 轻量：加入 `crossing_count`、kNN 边覆盖率、边长分位数、局部 2-opt 改进潜力估计等；
  2) 中等：把 tour 转成 successor/edge set，再用一个小的 edge-encoder 得到 `sol0_emb`；
  3) 重：做 `data+sol0` 的联合 encoder（GraphTransformer conditioned on tour）。

### P1.4 对不同 N 的泛化目前不清晰（pipeline 与 ckpt 都可能是 size-specific）
- 现象：
  - 训练脚本以 `problem_size` 固定构建 env/policy/solver。
  - 现实上 TSPLIB/真实数据 N 不一致；许多 EasyNCO 模型也按规模训练。
- 建议：
  - 在 `1two_gate/` 层面明确三种模式：
    1) 固定 N（当前）
    2) N 取值集合（例如 50/100/200），gate 输入显式包含 N，并且 solver 按 N 选 ckpt
    3) 真正可变 N（更难，需要 solver 支持、encoder 支持、eval 支持）

### P1.5 评估指标太少：缺少“选择质量”的分解视图
建议至少补齐：
- `oracle_len`、`regret`（见 P0.2）
- `win-rate`：每 solver 在实例级别赢的比例（初始化阶段/迭代阶段分别统计）
- `diversity`：gate 的有效支持集大小（熵/有效类别数）
- `stability`：不同 seed 下 gate 分布与 regret 的方差
- **按分布的版本**：上述每个指标都必须按 D 拆解（否则无法证明“分布专长”）

### P1.6 多分布混合训练时，reward 尺度/难度差异会“淹没”分布专长信号（需要分布层面的归一化/采样控制）
- 现象：
  - 你现在的训练是把多个分布混在一起采样（每实例随机选分布），reward 直接是 `-length`。
  - 但不同分布的“典型长度尺度”和“可改进空间”可能差异非常大（例如某些分布天然更长、或更容易被某类迭代器改进）。
- 为什么这是问题（对你“分布→策略”的目标是致命的）：
  - 如果不做分布层面的平衡，梯度会被“更难/更长/方差更大”的分布主导，gate 学到的可能是：
    - “先学会在难分布上别崩”，而不是“每个分布都学出不同的最优 pipeline”；
    - 或者 gate 被迫学一个折中策略，导致 action 分布在不同 D 上差异不明显（specialization 不成立）。
- 建议（优先级从易到难）：
  1) **分布分层 batch（stratified batch）**：每个 batch 强制包含各分布相同数量样本（而不是完全随机混合）
  2) **分布内 baseline / advantage normalization**：对每个分布 D 单独做 baseline（或 z-score 标准化），再把梯度汇总
  3) **分布均衡加权**：在 loss 中对不同分布加权，确保每个分布对更新贡献一致
  4) **训练-评估一致性**：eval 也按 D 单独汇报，否则你会误以为“总体更好”但某些分布其实更差

### P1.7 “分布专长”目标需要更清晰的对照：显式区分「知道分布」vs「从实例中推断分布」
- 背景：
  - 你希望 gate 学到 `x → (init, iter)` 的**分布条件策略**。
  - 但“分布专长”这句话本身有两个不同层次的命题，若不拆开做对照，很容易出现“看起来学到了，其实只是实验口径混乱”的风险。
- 需要拆成三个层次（建议你都做，并在论文/报告里明确）：
  1) **Oracle-by-D（知道分布标签）**：评估时直接用真实 `D` 选一个固定 pipeline（见 7.1）。这是“如果分布已知，最多能提升多少”的上限之一。
  2) **Gate-with-D（把分布标签喂给 gate）**：训练/推理时把 `D`（one-hot 或 embedding）作为 gate 输入的一部分。  
     - 这不是你最终想要的真实场景，但它是一个非常强的对照：可以验证“你的 zoo 的确存在分布专长”“你的 gate 容量足以利用分布信息”。
  3) **Gate-without-D（不提供分布标签）**：只给实例本身的特征，让 gate 自己从 `x` 推断分布差异。  
     - 这是你更接近真实研究目标的设置。
- 为什么这很重要：
  - 如果 (2) 能明显优于 best single pipeline，但 (3) 不能：说明主要瓶颈在“分布可识别性/特征不足/编码器不敏感”，而不是 RL 或两层 gate 架构。
  - 如果 (2) 和 (3) 都不能：优先怀疑“zoo 互补性不足/存在 dominate pipeline”（见 P0.3），或“训练信号/稳定性问题”（见 P1.1/P1.6）。
  - 如果 (3) 能接近 (2)：这是非常强的证据链，能够支撑你“从实例结构中学到了分布偏好”的主张。
- 最小改动建议（仍然只改 `1two_gate/`）：
  - 给 gate 增加一个可选开关：`use_dist_id_feature`（默认 False），为 (2) 提供快速 baseline。
  - 额外可选：加一个轻量的辅助头 `predict_D(x)`（多任务），用于迫使表示携带分布信息；但务必作为 ablation（不要强行把它当成主方法）。

## 4. P2：研究完整性/可扩展性相关的点（论文价值）

### P2.1 分布专长（specialization）需要“分布体系”本身清晰、可复现、可控
- 现状：
  - `1two_gate/tsp_data.py` 目前主要支持 `uniform` 与 `gaussian`（高斯混合/num_modes=0 退化为 uniform）。
  - 但你研究目标是“不同分布选择不同 pipeline”，这要求你的“分布集合”足够丰富，且每个分布的定义稳定。
- 建议（从强到弱）：
  1) **完全对齐论文的分布族**：把 paper 中的 `Explosion/Rotation/...`（或你关心的分布）纳入 `1two_gate/tsp_data.py`，并保证可用 seed 完全复现  
  2) **用平台已有数据集做分布 proxy**：例如直接用 `EasyNCO/data/datasets/cross_distribution` 中不同文件作为不同分布  
  3) 至少在实验报告中明确：每个“分布”的生成规则/参数范围/seed，避免“分布”只是口头描述

### P2.2 当 eval 不计成本时，你可以做更强的“诊断型实验”（这会显著提升论文说服力）
- 建议额外加入（全部按分布拆解）：
  - **全矩阵性能热图**：`mean len1(i,j|D)`（init×iter）  
  - **专长指数**：例如对每个 pipeline 定义 `specialization_score = Var_D( rank_D(pipeline) )` 或 `max_D (advantage_D)`  
  - **gate 的“分布条件混淆矩阵”**：分布 D → action 分布（a1/a2）  
  - **“难度 vs 机会”**：在某分布上 oracle 与次优之间的差距越大，gate 的价值越大（可用于解释为什么某些分布更能体现选择收益）

### P2.3 只做 on-policy REINFORCE，样本效率偏低
- 两层 gate 的离散动作空间会让方差更大；你若后续扩大 zoo、扩大 N，REINFORCE 可能会“学不动/学不稳”。
- 可选路线（从易到难）：
  1) advantage normalization + entropy bonus + gradient clipping（工程收益最大）
  2) PPO（对离散动作很友好）
  3) hierarchical RL / option-critic（如果你要把 pipeline 进一步细化）

### P2.4 缺少与“监督选择器”（原论文）对齐的对照实验
- 你的工作要说服别人，需要明确对照：
  - 监督学习选择器（用少量离线标签，或用小 zoo 全跑打标签）
  - 你的 RL 双 gate（不需要全组合标签）
  - 以及若干 ablation（不看 sol0、只看 length0、只训练 gate2 等）

### P2.5 工程层：配置/实验管理/日志与复盘仍偏“脚本化”
- 你已经有日志文件与解析工具，但要支撑论文级实验，建议补齐：
  - 运行环境快照（git hash / 依赖版本 / GPU 型号）
  - 每次实验的“命令行 + cfg + solver ckpt 列表”的完整记录
  - 自动汇总多个 seed 的表格输出（CSV/TSV）

## 5. 建议的路线图（可执行、分阶段）

下面给一个“先把研究信号做干净，再逐步扩展”的路线图。每个阶段都给出产物（DoD）。

### Phase 0（P0）：正确性与公平性基线（1–3 天）
- [ ] Gate2 特征避免重复 encoder forward（产物：训练速度明显提升；encoder forward 次数减半）

## 6. 评估协议（Length-only + Exhaustive + Per-distribution；且 eval 不计成本）

这一节是你设定里最“强”的杠杆：既然 eval 不计成本，你完全可以把证据链做成 reviewer 很难质疑的形态。  
你要证明的命题是：

> 不同分布 `D` 上，最优 pipeline `(init, iter)` 不同；Two-Gate 能从实例特征中识别分布差异，并选择接近 oracle 的 pipeline，从而显著降低 `length`。

为此，评估必须满足两个条件：
1) **Exhaustive**：把 `I×J` 的全组合都跑一遍（至少在 eval 阶段）  
2) **Per-distribution**：任何汇总指标都必须按分布拆解（否则看不到 specialization）

### 6.1 基本符号（建议你后续代码/日志/表格统一用这些列名）
- 分布集合：`D ∈ {uniform, gaussian, rotation, explosion, ...}`
- 初始化器集合：`I = {i_1, ..., i_|I|}`（即 `init_zoo`）
- 迭代器集合：`J = {j_1, ..., j_|J|}`（即 `iter_zoo`）
- 实例：`x`（一条 TSP 坐标）
- 长度：
  - `len0[i,x]`：用 initializer `i` 得到的初始解长度
  - `len1[i,j,x]`：在 `i` 的 `sol0` 上用 iterator `j` 改进后的最终长度（你的唯一对比口径）

### 6.2 Exhaustive 评估的“最小闭环”（必须实现）
对每个分布 `D` 的测试集 `X_D`：
1) 对每个 `i∈I`：跑一次 initializer 得到 `len0[i,x]`
2) 对每个 `(i,j)∈I×J`：从 `sol0(i,x)` 出发跑 iterator 得到 `len1[i,j,x]`
3) 实例级 oracle：
   - `oracle_len[x] = min_{i,j} len1[i,j,x]`
   - `oracle_pipeline[x] = argmin_{i,j} len1[i,j,x]`（可能多解并列，建议存 top-k）
4) gate 输出：
   - `gate_pipeline[x] = (i_hat(x), j_hat(x))`
   - `gate_len[x] = len1[i_hat(x), j_hat(x), x]`
5) regret（核心指标）：
   - `regret[x] = gate_len[x] - oracle_len[x]`（≥0）

### 6.3 强诊断：把 regret 拆成 Gate1 vs Gate2（你会非常快定位“没学到”的原因）
对任意实例 `x`，先定义：
- `best_len_given_i[x] = min_j len1[i,j,x]`

则：
- **Gate1 regret（选错 initializer 的代价）**：`r1[x] = best_len_given_i_hat[x] - oracle_len[x]`
- **Gate2 regret（给定 initializer 选错 iterator 的代价）**：`r2[x] = gate_len[x] - best_len_given_i_hat[x]`
- 恒等分解：`regret[x] = r1[x] + r2[x]`

意义：
- 如果 `r1` 大、`r2` 小：主要瓶颈在“识别分布/选初始化器”
- 如果 `r1` 小、`r2` 大：主要瓶颈在“根据 sol0 结构选迭代器”（Gate2 特征/建模不够）

### 6.4 分布专长（specialization）要输出的“四件套证据”
对每个分布 `D`，至少输出四类结果（最好固定成一张表 + 两张图 + 一个列表）：
1) **Pipeline heatmap（init×iter）**：矩阵 `mean_x len1[i,j,x]`（能直接看到该分布 top pipeline）
2) **Top pipelines**：列出 `D` 上平均最短的 top-5 pipeline，以及它们之间的差距（证明“最优者不同/互有胜负”）
3) **Gate action distributions**：`p(a1|D)`、`p(a2|D)`（证明 gate 行为随 D 变化）
4) **Regret distribution**：`E[regret|D]`、中位数、95 分位（看 tail 风险；只看均值不够）

### 6.5 “gate 是否真的在做分布选择”的量化指标（强烈建议加入）
只看 `mean_len` 不足以证明“分布专长”，你需要行为层面的统计：
- **互信息**：`I(D; a1)`、`I(D; a2)`（可用频率估计；越大表示越依赖分布）
- **分布间 action 差异**：`JS( p(a|D1), p(a|D2) )`（或 KL；JS 更稳健）
- **Top-k 命中率**：`gate_pipeline[x]` 是否落在 `oracle_pipeline_topk[x]`（k=1/3/5）

### 6.6 评估运行协议（为了可复现/可比较）
因为很多 solver/iterator 可能含随机性，你需要明确“评估口径”：
- **Decoder strategy**：greedy 还是 sampling（建议先 greedy，确保稳定；再做 sampling 的扩展）
- **随机种子**：对每个 `D` 建议至少跑 `seeds={0..9}`，并同时报告：
  - fixed-seed 的 mean（近似期望）
  - best-of-seeds（近似“重启/多次运行取最优”的上限）
- **一致性**：exhaustive eval 的每个 `(i,j)` 必须用同一套 `X_D`（同一批实例）才能公平比较

### 6.7 强烈建议把 eval 结果持久化（即使你不在乎开销）
eval 不计成本不代表你要重复跑：你后续会做大量 notebook 分析、画 heatmap、做 ablation。  
建议持久化三张表（CSV/TSV/Parquet 均可）：
- `instance_pipeline_len.tsv`：列 `(dist, instance_id, init, iter, len0, len1, seed, ...)`
- `instance_gate.tsv`：列 `(dist, instance_id, a1, a2, gate_len, oracle_len, r1, r2, ...)`
- `dist_summary.tsv`：列 `(dist, mean_gate_len, mean_oracle_len, mean_regret, p(a1|D), p(a2|D), ...)`

## 7. 实验矩阵（建议）与“成功标准”（你最终要看到的现象）

### 7.1 必须包含的 baseline（length-only）
所有 baseline 都要按分布 `D` 分别报告：
- **Best single pipeline**：固定一个全局 `(i*,j*)` 在所有分布上跑（“不做选择”的最佳水平）
- **Oracle-by-D（分布已知的上限）**：每个分布选一个固定 pipeline（看“如果知道分布标签，能提升多少”）
- **Instance oracle**：每实例最优 `(i,j)`（真正上限，用于 regret）
- **Ablations（定位 Two-Gate 的必要性）**：
  - 只用 Gate1：Gate2 固定一个 iterator（看“是否需要 Gate2”）
  - 只用 Gate2：Gate1 固定一个 initializer（看“是否需要 Gate1”）
  - Gate2 不看 sol0：只用 data embedding（看“sol0 条件信息是否真的有用”）

### 7.2 “成功现象”定义（你这篇工作的核心卖点）
在你的设定（只比 length、eval 不计成本）下，成功应当同时满足：
1) **专长存在性**：exhaustive heatmap 显示不同分布的 top pipeline 不同（至少 2–3 个分布发生 top-1 变化）
2) **行为分化**：`p(a1|D)`、`p(a2|D)` 在不同分布上明显不同（互信息/JS 显著；不是一个扁平分布）
3) **性能提升**：gate 在多个分布上显著优于 “best single pipeline”（否则选择没有意义）
4) **接近上限**：`E[regret|D]` 足够小，并且能解释主要来自 Gate1 还是 Gate2（`E[r1|D]` vs `E[r2|D]`）

### 7.3 推荐的最小实验矩阵（先把信号做清楚，再扩展）
建议先固定：
- `N`：先固定一个规模（例如 N=100 或 N=200），避免“规模差异”与“分布差异”纠缠
- `D`：先选 3–4 个分布（例如 uniform / gaussian-mixture / rotation / explosion）
- `I×J`：先选一个中等 zoo（例如 4–6 个 initializer + 2–4 个 iterator）

然后跑三组训练/测试：
1) **In-distribution**：train=all D，test=all D（看是否学到分布专长）
2) **Held-out distribution**：train=3 个分布，test=第 4 个分布（看泛化与 OOD 行为）
3) **Single-distribution training**：每次只训练一个分布（得到“专门化 gate”的对照）

## 11. TSP 实例特征清单（用于解释“为什么某分布/实例偏好某 pipeline”】【Length-only 语境下依然有价值】

这一节的目的不是“堆特征”，而是给你一个**可解释的特征菜单**：  
当你发现某分布 D 上 gate 更偏好某初始化器/迭代器时，你需要能用“实例结构”去解释它，而不是只报一个数字。

### 11.1 坐标分布/几何形状（从 coords 直接计算；成本低）
- **Anisotropy（各向异性）**：对坐标做 PCA，取 `λ1/λ2`（越大越“拉长”）。  
  - 直觉：拉长/带方向性的实例，局部边结构可能更稳定；某些模型若缺少旋转不变性，可能对方向敏感。
- **kNN distance stats（局部密度统计）**：对每个点计算 k 近邻距离（均值/方差/分位数），再对全体点做汇总（均值、CV、Gini）。  
  - 直觉：cluster 分布会表现为“局部很密、局部很稀”的高方差；uniform 更均匀。
- **Pairwise distance quantiles（全局距离分位数）**：采样一部分点对距离，取 10/50/90 分位。  
  - 直觉：能刻画“整体尺度/离散程度”，以及是否存在长边主导的结构。

### 11.2 图结构（由距离诱导的 kNN 图/MST；成本中等）
- **MST length / mean edge length**：构建最小生成树，记录总长度及边长分布。  
  - 直觉：MST 很短往往意味着点更聚集；MST 边分布也能反映“多簇结构”。
- **kNN graph clustering coefficient / degree stats**：在 kNN 图上算局部聚类系数等。  
  - 直觉：cluster 分布会形成更明显的局部团簇。

### 11.3 初始解结构（依赖 sol0；这是 Gate2 最应利用的信息）
- **len0（初始长度）**：最直接的“初始化好坏”指标。  
  - 注意：它只反映当前 initializer 的输出质量，不足以反映“可改进空间”。
- **Crossing count（交叉数）**：统计 tour 边的几何交叉次数（或近似）。  
  - 直觉：2-opt 类迭代器的收益与交叉数往往高度相关（交叉多→更容易改进）。
- **Edge length distribution（边长分布）**：tour 边长的分位数/长尾程度。  
  - 直觉：有些 destroy/repair 更擅长消除少量极长边；2-opt 更擅长局部交换。
- **2-opt potential（改进潜力估计）**：随机采样若干对边，估计平均可改进幅度（或最优改进）。  
  - 直觉：直接把“这个 sol0 还有多少局部改进空间”量化出来，通常比只看 len0 更有用。

### 11.4 使用建议（避免陷入“特征工程”）
- 先把特征用在 **分析/解释**（做相关性、做条件分布），确认它们确实能区分分布/解释行为。
- 再决定哪些特征值得喂给 Gate2；否则你很容易把系统变成难以维护的 feature pipeline。

## 12. “不同分布→不同 pipeline”要成立，你的分布集合与 zoo 必须共同满足的条件（实验设计要点）

你当前的三点设定中，(2) 是研究目标；但它不是“训练多跑几次就自然出现”的性质，更多取决于**实验设计是否让它有机会出现**。

### 12.1 两类分布移位（它们触发“专长差异”的机制不同）
1) **结构性移位（distance matrix 结构改变）**：例如 uniform vs clustered/mixture。  
   - 这类移位会改变最优 tour 的局部结构（边长分布、局部密度差异等），理论上更容易产生“不同迭代器有效性不同”。
2) **表征性移位（距离不变但坐标表征变）**：例如旋转/翻转/尺度变换。  
   - 对 TSP 的最优长度与距离矩阵来说，纯旋转并不改变问题本身；  
   - 但神经求解器若没有学到对应不变性，性能可能会变，从而产生“某些模型更鲁棒”的专长差异。

### 12.2 zoo 设计原则（只看 length、且 eval 不计成本时更要注意）
- **避免 dominate pipeline**（见 P0.3）：否则 gate 的最优策略会退化成常数函数。
- **把“方法/超参”都当成 pipeline 的一部分**：
  - 例如同一个方法不同的 `augmentation`、不同的 `T`/`steps`，在你“不考虑 eval 开销”的设定下，本质上就是不同 pipeline 候选。
  - 但要小心：如果你把某个方法的预算开得极大，它很可能在所有分布上都 dominate。
- **先用 exhaustive eval 画地图，再决定 zoo**：
  - 这一步在你的设定下几乎是“免费的”，但能极大减少你后续在训练上浪费的时间。

### 12.3 最稳健的实验闭环（推荐你严格按这个顺序做）
 1) 固定 `N` 与坐标尺度（避免 length 口径被 N/scale 混淆）
 2) 选 3–4 个分布，跑一次 exhaustive heatmap，确认 top pipeline 在不同 D 上确实不同
 3) 在这个“有专长差异”的设置上训练 Two-Gate
 4) 报告：best single pipeline vs gate vs oracle-by-D vs instance oracle，并给出 r1/r2 分解与 `p(a|D)` 行为证据

## 13. 对结果影响很大的“初始化/推理参数”清单（不仅是 ckpt / aug / DACT 的 P）

你提到的三个例子非常关键：  
**(1) 同一方法不同 ckpt**、**(2) augmentation 参数**、**(3) DACT 的 `P`（no-improvement restart threshold / patience）**。  
但在 NCO（尤其是神经求解 + 可选局部搜索）里，“最终 length”往往对一组“看似只是推理细节”的参数极其敏感。为了让你的 Two-Gate 项目结论可信，你需要把这些参数视为 **pipeline 的一部分**，并在实验里显式固定/记录/对照。

下面给出一个尽量全面、可直接用于实验记录的参数清单（按“对 length 影响机制”分类）。

### 13.1 Checkpoint 与训练态相关（同一方法内部差异最大的一类）
- **ckpt 版本/epoch/选择规则**：
  - best-val vs last-epoch vs EMA（指数滑动平均）权重；  
  - 不同 epoch 的“过拟合/欠拟合”会显著影响 OOD 分布的表现。
- **训练配置差异导致的“同名方法”不可直接比较**：
  - 例如是否做 augmentation 训练、是否用更强 baseline、是否 meta-learning、是否用不同的 normalization/batchnorm 策略。
- **尺度专用 ckpt（按 N 训练）**：
  - 很多方法实际上是 size-specific 的（TSP50/TSP100/...）。  
  - 在你的设定里，“按 N 选 ckpt”属于 pipeline 规则的一部分；不显式定义会导致结论摇摆。

### 13.2 解码/采样策略（decoder_strategy/temperature/beam/多轨迹）
这类参数在“构造式”方法上尤其敏感：
- **greedy vs sampling**：
  - sampling 往往能显著降低期望 length（尤其配合多次运行取 best），但方差也更大。
- **temperature / top-k / top-p**：
  - 温度越高探索越强，可能更好也可能更差；不同分布下最优温度可能不同。
- **beam search 宽度**（如果实现支持）：
  - beam 更大通常更强，但也可能改变“专长地图”（某方法在某分布突然 dominate）。
- **并行轨迹数 / group_size / sample_size**：
  - POMO 类的 `pomo_size`、OMNI/ELG 的并行采样数、HTSP/其它方法的 `sample_size`，都会显著影响最优 length。
  - 在你“不考虑 eval 开销”的设定下，这些参数如果不固定，就会把问题退化成“谁跑得多谁更强”，从而掩盖“分布→策略”的研究信号。

### 13.3 Augmentation（不仅是次数，还包括“口径”）
- **aug 类型**：rotate/reflect/pomo_aug/...（是否真的是“等价变换”）  
- **aug 次数/因子**：`aug_factor`（越大通常更强）  
- **聚合规则**：多次 augmentation 的结果是取 **min-length**、还是 average、还是投票？  
  - 对 length-only 的评估，通常取 min-length 会显著抬高上限，且会放大方法间差异。
- **aug 与 sampling 的组合**：
  - `aug_factor × num_samples` 的组合会让“有效运行次数”暴涨；若不记录，你会误以为某方法“天然更强”。

### 13.4 迭代预算与停止条件（迭代式方法最敏感）
- **最大步数 / T_max / max_steps**：
  - 这是决定最终 length 的头号因素之一（更多步通常更好，但也可能陷入局部/重启频繁）。
- **重启机制与阈值（patience）**：
  - DACT 的 `P` / TSPLIB 里的 `Tr`（no-improvement threshold）这类参数，会改变“探索 vs 收敛”的平衡。
- **重启次数上限 / 多次独立运行取 best**：
  - 本质上也是 budget；在你不计 eval 开销时，这会让迭代式方法极易 dominate。
- **接受准则（acceptance）/ 回退策略**：
  - 例如仅接受改进、允许小幅变差（类似 simulated annealing 的思想）、或按概率接受；这些都会改变最终质量。

### 13.5 邻域/候选集相关（local neighborhood 的强弱）
- **kNN 候选边大小 / local_size / fragment 参数**：
  - 候选集越大越强，但代价更高；候选集太小会直接限制可达解空间，造成“怎么调都上不去”的假象。
- **片段长度/拼接策略**（如 HTSP/fragment 类方法）：
  - `frag_len`、`max_new_nodes` 等会影响“高层拼接是否可行”和“低层改进的自由度”。

### 13.6 距离口径与坐标预处理（非常容易被忽略，但会让对比失效）
- **坐标 scale/normalize/center**：
  - 如果一个方法内部对坐标做了 normalize，而另一个方法没有（或 normalize 方式不同），即使最终都在同一 env 下算 length，也会影响模型输出分布（尤其是 attention 的数值范围）。
- **距离定义**：Euclidean（连续） vs TSPLIB 的 EUC_2D/CEIL_2D（整数/取整）  
  - 你的 Two-Gate 设定是 length-only，但仍需要保证所有方法都在同一口径下评估，否则“谁更强”就没有意义。

### 13.7 随机性与确定性（你会误判“分布专长”的主要来源）
- **seed**：影响 sampling、dropout（如果没关）、以及某些局部搜索的随机选择  
- **deterministic 相关开关**：CUDA 算子非确定性可能导致小幅漂移；在“差距很小”的实例上会直接改变 winner。
- **eval 模式是否正确**：`model.eval()` / `torch.no_grad()` / batchnorm 的 running stats 是否稳定。

### 13.8 给 Two-Gate 项目的一条硬建议（避免后期不可解释）
把“方法 + 关键推理超参”当成一个不可拆分的对象：  
你后续无论做 exhaustive heatmap 还是做训练，都建议用一个明确的 `PipelineSpec`（哪怕只是字典/字符串）记录：
- `name`（方法名）
- `ckpt_id`（或路径/版本）
- `decoder`（greedy/sampling + 温度/beam）
- `aug`（类型+次数+聚合）
- `budget`（并行轨迹数/迭代步数/重启阈值等）

否则你很难回答 reviewer 最常问的一句话：  
“你说 gate 学到了分布偏好，但它是不是只是在利用你给某些方法开了更大的推理预算？”

## 14. 构造式 vs 迭代式：对“Two-Gate + length-only”设定的影响

你提到的观察非常重要：**迭代式方法的初始化往往“理所应当”更差**，因为它们的设计目标不是“一步给出好 tour”，而是“从一个（可能很差的）起点不断改进”。

### 14.1 两类方法的本质差异（从 TSP 的角度）
- **构造式（constructive）**：
  - 直接从空解开始逐步构造一个完整 tour（自回归/并行构造/扩散生成都属于这类“直接输出解”的范式）。
  - “初始化输出”基本就是它的最终解（或只需很少 post-process）。
- **迭代式（iterative）**：
  - 先拿到一个起始 tour（可能随机/贪心/启发式），然后用 2-opt / destroy-repair / policy-guided local search 等不断改进。
  - “初始化 tour 的质量”并不是它的强项；它的强项在“能改进多少、能否逃离局部最优”。

### 14.2 对你的 Two-Gate 设计意味着什么
- **init_zoo 更适合放构造式**：
  - 因为 Gate1 的职责是给 Gate2 提供一个“有信息含量的 sol0”（不仅仅是 length0，还包括结构）。
  - 如果 Gate1 选到一个迭代式方法但只跑初始化（几乎等于随机 tour），会让 Gate2 的学习变成“在垃圾起点上挣扎”，从而掩盖真实的“组合偏好”。
- **iter_zoo 更适合放迭代式**：
  - 因为 Gate2 的职责就是“给定 sol0，选最合适的改进机制”。
  - 这恰好对应你想研究的 `data + sol0 → iterator choice`。

### 14.3 一个常见的“口径陷阱”（需要在 plan 与实验里明确写出来）
- 如果你做任何“只跑初始化、不跑迭代”的对比（哪怕只是 sanity check）：
  - 构造式方法会天然占优；
  - 迭代式方法会被系统性低估；
  - 从而你会得到一个错误结论：“迭代式方法不行/不适合某分布”，但其实它只是还没开始发挥。

在你当前设定下（最终只看 `length(sol1)`，且 eval 不计成本），你完全可以：
- 为迭代式 iterator 给足预算（T/steps/restarts）来让它发挥；
- 同时在论文/报告里把它们清晰地定位为 **Gate2 的候选**，而不是 Gate1 的候选。

### 14.4 对“组合偏好”的一个关键启示（也是 Two-Gate 的研究卖点）
- 迭代式方法的收益往往强依赖初始解结构：  
  例如 2-opt 对“交叉多”的 sol0 可能收益极大，对“已很平滑”的 sol0 收益很小；  
  destroy-repair 对“存在少量极长边”的 sol0 可能更有效。
- 这意味着 Two-Gate 的价值恰恰在于：  
  让 Gate1 负责“生成不同类型的 sol0”，让 Gate2 负责“识别哪种改进机制最匹配这个 sol0”。

## 15. 项目可能的不可行性/高风险点（以及如何尽早证伪）

这一节专门回答你的第 3 点：这个方向有哪些地方可能“做着做着发现不成立/不值得”，以及你应当用什么最快的实验把它证伪（避免在错误假设上堆工程）。

### 15.1 （研究层）可能根本不存在“分布专长地图”
- 表现：
  - exhaustive heatmap 发现：某个 pipeline 在所有分布上都最好（或几乎最好），或不同分布的 top pipeline 差异极小。
- 后果：
  - Two-Gate 的最优策略退化成常数函数（总选同一个），你的核心命题 (2) 无法成立。
- 最快证伪：
  - 按第 6 节先做一次全矩阵评估（少量分布 + 中等 zoo 即可）。
- 可能修正：
  - 改 zoo（去掉 dominate pipeline / 增加互补性）、改分布族（选更结构性差异的分布）、或引入预算约束（见 15.3）。

### 15.2 （学习层）分布差异可能“从实例特征中不可识别”
- 表现：
  - Gate-with-D 明显优于 best single pipeline，但 Gate-without-D 做不到（见 P1.7）。
- 可能原因：
  - 你选的“分布差异”本质上是对问题等价的变换（例如纯旋转），对距离矩阵并不改变；  
  - 或者你用的 encoder/特征不足以捕捉差异。
- 最快证伪：
  - 做 (2) vs (3) 的对照（P1.7），并观察 `I(D;a)`/JS 是否接近 0。
- 可能修正：
  - 换分布（更结构性）、增强特征（第 11 节）、或做多任务辅助预测分布（作为 ablation）。

### 15.3 （设定层）在“eval 不计成本”下，问题容易退化成“预算越大越强”，从而掩盖选择的意义
- 表现：
  - 你把 aug_factor / sample_size / T_max 开大后，某方法迅速 dominate；选择问题消失。
- 这并不是实现 bug，而是“问题定义风险”：
  - 如果预算无限，理论最优就是“全跑一遍所有 pipeline 取最短”（instance oracle）；  
  - 这会让 gate 的意义变成“省计算”，但你又明确不考虑开销 → 逻辑上会变得尴尬。
- 最小化风险的建议（不违背你的设定）：
  - **仍然固定一个合理 budget** 来定义“可比较的 pipeline 集合”；  
  - 然后在这个 fixed-budget 集合里研究分布专长与选择收益。  
  - 你可以在附录里再做“budget sweep”（展示预算增加后的上限），但主结论必须在固定 budget 下成立。

### 15.4 （工程层）pipeline 组合存在“接口/假设不兼容”，导致结果随机崩坏或不可解释
- 典型风险：
  - 某些 iterator 隐含假设 sol0 具有特定结构/分布（例如需要一定随机性或特定编码），否则会出现非常不稳定的行为；
  - 不同方法对坐标 normalize 的假设不同，导致输出分布怪异；
  - 设备/精度/默认 tensor type 混用导致偶发错误（你已经遇到过类似问题）。
- 最快证伪：
  - 在 eval 脚本里对每个 `(init,iter)` 做基本 sanity checks：
    - tour 是否是合法排列、是否包含重复/缺失节点；
    - length 是否为有限值、是否出现 NaN/Inf；
    - 记录失败率并把失败 pipeline 从 zoo 中剔除或单独分析。

### 15.5 （训练层）两层 gate 的 credit assignment 可能导致“学不动/学到错误归因”
- 表现：
  - Gate1/2 很快塌缩到某个动作；不同 seed 差异巨大；或 regret 不降但熵在降。
- 最快证伪：
  - 做 `regret = r1 + r2` 分解（第 6.3 节）：  
    - 如果 r1 长期占主导，说明 Gate1 不会选初始化器；  
    - 如果 r2 长期占主导，说明 Gate2 不会利用 sol0。
- 可能修正：
  - entropy bonus、per-dist baseline、分布分层 batch（P1.1/P1.6），或先做 curriculum（先只学 Gate1，再解锁 Gate2）。

### 15.6 （可复现性层）你依赖多个外部方法与 ckpt，复现链条很容易断
- 表现：
  - 某个 ckpt 缺失/格式不兼容/版本不匹配，导致“同一方法”在不同机器上结果不同。
- 最快证伪：
  - 把 `PipelineSpec`（第 13.8 节）与所有 ckpt 的 hash/来源写入实验产物；  
  - 让任何人拿到这些信息就能复现实验（至少在你的环境里可复跑）。

### 15.7 “不可行性”的最终判据（建议你写在项目里作为 stop condition）
如果你做完以下两步仍然看不到清晰信号，就应当考虑及时止损或调整研究问题：
1) 在固定 budget 下，exhaustive heatmap 显示不同分布 top pipeline 明显不同（专长存在性）  
2) Gate-without-D 能在多个分布上显著优于 best single pipeline，并且 `I(D;a)`/JS 显著（行为分化）

如果 1) 不成立：是实验设计/问题定义问题；  
如果 1) 成立但 2) 不成立：是特征/学习问题（可能需要更强表征或不同训练范式）；  
如果 1) 和 2) 都成立：你的方向就很扎实，后续主要是扩展与写作。

## 16. 模型设置层面的“问题/不可行性”（基于 `EasyNCO/settings/*.yaml` 的实际字段）

下面这些点都属于“只看 length 时最容易把结论搞乱/搞崩”的**设置层风险**（不是实现 bug），而且多数都能从配置文件里直接看到：

- **预算不对齐 → 选择问题退化**：`env.aug_factor`（如 `omni/elg/icam` 常见为 8）+ `env.pomo_size`（如 `elg/icam` 用 `${scale}`，而 `lehd` 是 1）+ `iteration_params.max_steps`（如 `lehd_settings.yaml` 默认 10，但 `dact_settings.yaml` 默认 1000；而 DACT 论文常见对比是更大的 `T` 如 3k/10k）会把“谁更强”几乎完全变成“谁预算更大”。不固定就无法谈“分布偏好”。
- **同一方法内部的“设置组合爆炸”**：以 `omni_settings.yaml` 为例，`module.initialization_params.meta_params`（meta_method/data_type/B/k/meta_batch_size/solver/...）+ `module.fine_tune.enable` 会让“同一个方法”在推理时表现像完全不同的 solver。Two-Gate 若不把这些固定，结论不可解释。
- **问题类型默认值可能不匹配**：例如 `EasyNCO/settings/omni_settings.yaml` 与 `EasyNCO/settings/dact_settings.yaml` 的 `env._target_` 默认是 `CVRPEnv`（不是 TSP）。如果你没显式覆盖，可能出现“跑得起来但口径不对/或直接崩”的情况。
- **强 size-specific 假设**：`dact_settings.yaml` 里 `model.problem_size: ${scale}` + 代码里常需要显式初始化 problem size（否则会出现 pattern/position-encoding 的形状错配）。这意味着：同一 ckpt 在不同 N 上不仅性能变，还可能直接不可用。
- **HTSP 的低层 solver 配置对 N 极敏感**：`htsp_settings.yaml` 里 `model.low_level.group_size: 200`、`frag_len: 200`、`low_env.max_new_nodes: 190` 等是“硬超参”。对小 N（例如 TSPLIB 50~200）很容易出现 shape/memory/缓冲区不匹配；对大 N 又可能算力需求暴涨。
- **配置里存在“路径/环境依赖”**：例如 `htsp_settings.yaml` 的 `low_level.lower_path: '/pretrained/htsp_lower_tsp.ckpt'` 是绝对路径风格；不同机器/目录结构下很容易断。只要断一次，你就会被迫改配置或加映射逻辑，复现链条变脆弱。
- **Normalization/架构差异会伪装成“分布专长”**：`omni` 用 `normalization: batch_no_track`，`icam/elg` 常用 `instance`，`dact` 用 `layer`，`lehd` 甚至是 `None`。这些选择会显著影响 OOD 泛化与尺度敏感性；Two-Gate 学到的“偏好”有可能只是在利用这些设置差异，而不是方法本质差异。
- **论文口径 vs 配置默认值不一致**：例如 `elg_settings.yaml` 默认 `local_enable: False`（若论文/原实现包含 local refinement，则你这里会系统性偏弱），以及不同方法默认的 `normalization/层数/heads` 与论文设定不一致时，会让“方法对比”变成“复现细节对比”。
- **decoder_strategy / 多次运行口径不一致**：很多论文报告的是 sampling / 多次运行取 best / augmentation 汇总；如果你全局只用 `decoder_strategy=greedy` 或只跑单次，会系统性低估这些方法（而 `pomo_size/aug_factor` 又在另一侧放大它们）。这会直接扭曲你要学习的“选择地图”。

一句话总结：在你“只比 length、eval 不计成本”的设定下，**最危险的不是训练不收敛，而是你没有把“预算/设置”当成 pipeline 的一部分来固定或显式建模**；那样你得到的任何“分布偏好”都可能是配置噪声，而不是实例结构偏好。
